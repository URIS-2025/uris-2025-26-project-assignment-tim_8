# Task 004: OrganizationService Notification Producer (Agent C)

**Type:** code
**Dependencies:** 001

## Goal
Make OrganizationService produce a **system notification** when (a) a new manager/user is added to an organization and (b) a user's role changes. The org-id is known directly here (no box resolution needed). Fire a non-fatal notification call forwarding the caller's JWT. Add unit tests.

## Acceptance criteria
- [ ] New user/manager added → one system notification with the org's `OrganizationId` + sensible `Text` (e.g. "A new member was added to your organization.").
- [ ] Role change → one system notification with the org's `OrganizationId` + sensible `Text` (e.g. "A member's role was changed.").
- [ ] Notification call non-fatal (task 001 contract); caller's `Authorization` header forwarded.
- [ ] Named `HttpClient` for `SystemNotificationService` registered in `Program.cs`; URL in `appsettings.json` `Services` section.
- [ ] Unit tests (xUnit + Moq, in `OrganizationServiceTests/`): notification client called once per event with correct org-id; notification-client-throws → underlying add/role-change still succeeds.
- [ ] `dotnet build` and the OrganizationService tests pass.

- **Read task 001's "Findings / Solution" first** — DTO shape, route, non-fatal client template.
- Controllers to instrument: `OrganizationService/Controllers/UserController.cs` (add user/manager) and `OrganizationService/Controllers/UserRoleController.cs` (role change). Inspect both to find the create/add and role-update actions; mirror the existing `LoggerServiceClient.TryLogAsync` usage + `Authorization` forwarding.
- Existing client to mirror: `OrganizationService/Clients/LoggerServiceClient.cs`; existing duplicated DTO `OrganizationService/Clients/LogCreationDTO.cs`. Add `Clients/SystemNotificationCreationDTO.cs` the same way, plus a `SystemNotificationServiceClient` with non-fatal `TryNotifyAsync(...)` → `POST /api/SystemNotification`.
- System notification DTO fields (local copy): `Text`, `OrganizationId (Guid?)`, `AnonymousUserId (Guid?)`, `ProblemCommentId (Guid?)`, `SuggestionCommentId (Guid?)`. For membership/role events set only `OrganizationId` + `Text`; leave the others null.
- The user entity in OrganizationService already carries its `OrganizationId` — read it off the entity/DTO being created or updated; **no box lookup needed** (this is the simplest producer).
- `Program.cs` registration: copy the existing `LoggerService` named-client idiom; confirm exact `Services:*` keys by reading `OrganizationService/Program.cs` + `appsettings.json`.

## Gotchas
- Never make the notification fatal.
- Keep the wire body to receiver-bound fields (task 001 contract).
- Distinguish "role change" from an ordinary user update — only fire the role-change notification when the role actually changed (compare old vs new role), to avoid noise.
- Mock the notification client in tests (extract a small interface if needed). Tests use `EF InMemory` + Moq.
