# Task 005: SubscriptionService Billing Producers (Agent D)

**Type:** code
**Dependencies:** 001

## Goal
Make SubscriptionService produce **billing notifications** for: plan/price change (fan-out to ALL orgs subscribed to that plan), payment success, payment failure, and subscription cancellation. Add a SubscriptionPlan **update** endpoint and a **subscriptions-by-planId** lookup to drive the fan-out. Make the existing subscription-create billing call **non-fatal**. Add unit tests.

## Acceptance criteria
- [ ] New `PUT api/SubscriptionPlan` update endpoint exists; on a plan/price change it fans out **one billing notification per org** that has a subscription to that plan.
- [ ] A "subscriptions by planId" lookup exists (repo method + the controller/code path that uses it) returning every subscription/org on a given plan.
- [ ] Payment success → billing notification to the paying org; payment failure → billing notification to the paying org. (Wire into `PaymentController` create/update.)
- [ ] Subscription cancellation → billing notification to that org. (Cancellation is currently `SubscriptionController.Delete` — confirm whether cancel == delete in this codebase and notify accordingly.)
- [ ] Existing subscription-**create** billing call made non-fatal: `BillingServiceCall.CreateBillingNotificationAsync` no longer throws on non-2xx (wrap like `TryLogAsync`); `SubscriptionController.Create` keeps working even if billing is down.
- [ ] All billing calls forward the caller's `Authorization` header (needed once task 006 adds `[Authorize]`).
- [ ] Unit tests (xUnit + Moq, in `SubscriptionServiceTests/`): plan-update fan-out creates N notifications for N subscribed orgs; payment success/fail each notify once; cancellation notifies once; non-fatal — billing client throws → underlying create/update/delete still succeeds.
- [ ] `dotnet build` and the SubscriptionService tests pass.

## Findings / Solution

SubscriptionService now produces **billing notifications** for plan change (fan-out),
payment success/failure, and subscription cancellation; the existing subscription-create
billing call was made non-fatal. Follows the task 001 contract.

**Data-model note (important):** `SubscriptionPlan` has NO price field — only `Title` +
`Description`. So "plan/price change" is modeled as a **plan update** (PUT). Cancellation is
modeled as **delete** (`SubscriptionController.Delete`) — there is no status-based cancel in
this codebase. `PaymentCreationDTO`/`PaymentCreatedDTO` carry no status, so payment
success/failure is mapped to the create **try** (success) vs **catch** (failure) paths.

**Non-fatal billing client (`ServiceCalls/BillingServiceCall.cs`):**
- Rewrote `CreateBillingNotificationAsync` from the throwing version to try/catch-swallow +
  800 ms timeout, forwarding the caller's `Authorization` header. Signature now
  `(BillingNotificationCreateDTO dto, string? bearerHeader = null, CancellationToken ct = default)`.
- Added parameterless ctor + made the method `virtual` so it's Moq-able. Existing callers
  (one-arg) still compile via default params.

**Repositories:**
- `ISubscriptionRepository.GetSubscriptionsByPlanId(Guid planId)` (+ impl: `Where(s =>
  s.SubscriptionPlanId == planId)`) — drives the fan-out.
- `ISubscriptionPlanRepository.UpdatePlan(SubscriptionPlanDTO)` (+ impl, returns null if
  the plan id doesn't exist) — backs the new PUT.

**Controllers:**
- `SubscriptionPlanController`: new `PUT api/SubscriptionPlan` (`Update`). On success it
  fans out **one billing notification per org** subscribed to the plan
  (`GetSubscriptionsByPlanId` → loop). 404 if plan missing (no fan-out). Injects
  `ISubscriptionRepository` + `BillingServiceCall`. Fan-out wrapped in try/catch (non-fatal).
- `SubscriptionController.Create`: existing billing call routed through new private
  `TryNotifyBillingAsync` (controller-level try/catch + bearer forwarding) → now non-fatal.
- `SubscriptionController.Delete` (cancellation): resolves org via `GetSubscriptionById`
  BEFORE delete, then non-fatal cancellation billing notification (skips if subscription
  null).
- `PaymentController.CreatePayment`: success path → "Payment processed successfully."
  notification to the paying org (PaymentId = created id); failure path (catch) → "Payment
  failed." notification (PaymentId = new guid). Org resolved via payment's
  `SubscriptionId` → `ISubscriptionRepository.GetSubscriptionById().OrganizationId`. Injects
  `ISubscriptionRepository` + `BillingServiceCall`; resolution+notify wrapped non-fatal.

**Wire body:** kept to the receiver-bound fields (`Text`, `OrganizationId`, `PaymentId`); the
outgoing DTO still carries the extra `Type` (ignored by the receiver, per task 001).

**DI:** no `Program.cs`/`appsettings.json` changes needed — `BillingServiceCall`,
`ISubscriptionRepository`, and the `BillingNotificationService` named HttpClient were already
registered/configured.

**Tests** (`SubscriptionServiceTests/`, xUnit + Moq; `BillingServiceCall` mocked via the new
parameterless ctor + `virtual`, controllers given a `DefaultHttpContext`):
- Plan update: fan-out creates **N notifications for N subscribed orgs** (N=3); plan-missing
  → 404 + no fan-out; no subscribers → Ok + zero notifications; billing throws → still Ok.
- Payment: success notifies the paying org once; failure (repo throws) notifies once with
  "failed" text + returns BadRequest; subscription missing → skip + still Created; billing
  throws → still Created.
- Cancellation: notifies owning org once; subscription missing → skip + still deletes;
  billing throws → still deletes.

**Verification:** `dotnet test SubscriptionServiceTests` → **102 passed, 0 failed** (91
pre-existing + 11 new).

**Note for task 006:** once `[Authorize]` lands on `BillingNotificationController`, all the
billing calls above already forward `Request.Headers["Authorization"]`, so they keep working.
