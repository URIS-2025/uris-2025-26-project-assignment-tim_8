# Task 001: Notification Contract (Phase 0)

**Type:** both
**Dependencies:** none

## Goal
Lock the shared conventions every producer (tasks 002–005) and the notification services (task 006) must follow: the two create-DTO shapes + routes, the `[Authorize]` + JWT-forwarding rule, and the **non-fatal notification client** pattern. This is a small, single-pass task whose output is mostly a written contract appended to this file (the "Findings / Solution" section) plus, optionally, a reusable client template. It blocks all parallel work — finish it first.

- [ ] The exact JSON body and route for creating a **billing** notification is documented (verified against `BillingNotificationController` + `BillingNotificationCreationDTO`).
- [ ] The non-fatal client pattern is specified as a copyable template (try/catch-swallow + 800ms timeout, forward `Authorization` header), modeled on `LoggerServiceClient.TryLogAsync`.
- [ ] The `[Authorize]` + JWT-forwarding convention is written down: notification controllers get `[Authorize]`; every producer forwards `Request.Headers["Authorization"]`.
- [ ] The org-id resolution rule is documented: producers resolve `BoxId → OrganizationId` via `GET api/<Box>/{id}`; comments/votes resolve parent → box → org; box-missing must NOT throw (notification is skipped).

## Context

### Existing reference pattern — the non-fatal client (COPY THIS SHAPE)
`ProblemService/Clients/LoggerServiceClient.cs`:
```csharp
public async Task TryLogAsync(LogCreationDTO dto, string? bearerHeader, CancellationToken requestCt)
{
    try
    {
        using var req = new HttpRequestMessage(HttpMethod.Post, "/api/logger");
        if (!string.IsNullOrWhiteSpace(bearerHeader))
            req.Headers.Authorization = AuthenticationHeaderValue.Parse(bearerHeader);
        var opts = new JsonSerializerOptions(JsonSerializerDefaults.Web);
        req.Content = JsonContent.Create(dto, options: opts);
        using var timeoutCts = new CancellationTokenSource(TimeSpan.FromMilliseconds(800));
        using var linked = CancellationTokenSource.CreateLinkedTokenSource(requestCt, timeoutCts.Token);
        using var res = await _http.SendAsync(req, linked.Token);
    }
    catch { }
}
```
The named client is created in `Program.cs` via `factory.CreateClient("LoggerService")`. Each producer service must register a `"SystemNotificationService"` (and SubscriptionService a `"BillingNotificationService"`) named `HttpClient` with a base address pulled from `appsettings.json` `Services` section, then register the client wrapper as scoped/transient. Inspect any service's `Program.cs` + `appsettings.json` to copy the exact registration idiom — note the existing `BillingNotificationService` client registration in `SubscriptionService/Program.cs`.

### Counter-example — the FATAL pattern to fix (do NOT replicate)
`SubscriptionService/ServiceCalls/BillingServiceCall.cs` currently **throws** on non-2xx:
```csharp
public async Task CreateBillingNotificationAsync(BillingNotificationCreateDTO dto)
{
    var response = await _httpClient.PostAsJsonAsync("/api/billingnotification", dto);
    if (!response.IsSuccessStatusCode) { ... throw new Exception(...); }
}
```
Task 005 makes this non-fatal. The contract: notification production must never throw into the caller.

- Producers in tasks 002/003/004 create their OWN local copy of this DTO under their `Clients/` folder (matching how `LogCreationDTO.cs` is duplicated per service) — do not add a cross-project reference.

### Billing notification create — route & DTO
- Route: `POST /api/BillingNotification` (controller `[Route("api/[controller]")]`, class `BillingNotificationController`).
- Receiving `BillingNotificationCreationDTO` (`BillingNotificationService/Models/DTOs/BillingNotificationDTO/BillingNotificationCreationDTO.cs`):
  ```csharp
  public string Text { get; set; }
  public Guid OrganizationId { get; set; }
  public Guid PaymentId { get; set; }
  ```
- NOTE the mismatch: SubscriptionService's outgoing `BillingNotificationCreateDTO` (under `SubscriptionService/Models/ExternalDTOs`) currently includes a `Type = TypeSubject.BillingNotification` field that the receiver DTO above does NOT declare. Document this — task 005 should keep the wire body to fields the receiver actually binds (`Text`, `OrganizationId`, `PaymentId`). `PaymentId` is required (non-nullable); for events without a real payment use an appropriate id or `Guid.NewGuid()` consistent with the existing create call.

### Org-id resolution
- `ProblemBoxService`: `GET api/ProblemBox/{id}` returns a `ProblemBoxDTO` carrying `OrganizationId`. (Also `GET api/ProblemBox/organization/{id}`.)
- `SuggestionBoxService`: `GET api/SuggestionBox/{id}` returns a `SuggestionBoxDTO` carrying `OrganizationId`. (Also `GET api/SuggestionBox/organization/{organizationId}`.)
- Problems/Suggestions carry `BoxId`, not `OrganizationId`. Comments resolve through their parent problem/suggestion → box → org. Votes resolve through suggestion → box → org.
- If the box lookup fails or returns null, the producer must skip the notification silently (no throw).

### Gotchas
- Notification calls are fire-and-non-fatal; never `await` them in a way that surfaces exceptions to the user response.
- Existing controllers already forward `Request.Headers["Authorization"]` into `TryLogAsync` — reuse the same value for notification calls.
- Once `[Authorize]` is added to notification controllers (task 006), producers that fail to forward a valid bearer will silently get 401 and the (non-fatal) notification will be dropped — so JWT forwarding is mandatory, not optional.
