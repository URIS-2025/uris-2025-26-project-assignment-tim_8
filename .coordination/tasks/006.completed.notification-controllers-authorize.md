## Goal
Protect both notification controllers with `[Authorize]` (so unauthenticated requests get 401), wire up auth in `Program.cs` if missing, and verify CRUD still works for authenticated callers. This runs in parallel with the producers — it depends only on the contract (001), not on the producers landing.

## Acceptance criteria
- [ ] `SystemNotificationController` has `[Authorize]` at the controller level.
- [ ] `BillingNotificationController` has `[Authorize]` (currently the attribute is present but commented out — `//[Authorize]`).
- [ ] Both services have JWT auth wired in `Program.cs` (`AddAuthentication`/`AddJwtBearer` + `app.UseAuthentication(); app.UseAuthorization();`). If missing, add it copying the convention from a service that already authenticates (e.g. AnonymousUserService or any producer service).
- [ ] CRUD endpoints still function for an authenticated caller (GET/POST/PUT/DELETE as applicable).
- [ ] Unit/controller tests assert `[Authorize]` is enforced: a request without a token gets 401. (Billing already has test scaffolding under `BillingNotificationServiceTests/`; SystemNotification under `SystemNotificationServiceTests/`.)
- [ ] `dotnet build` and both notification services' tests pass.

## Context

- **Read task 001's "Findings / Solution" first** — the `[Authorize]` + JWT-forwarding convention.
- Controllers:
  - `SystemNotificationService/Controllers/SystemNotificationController.cs` — class `SystemNotificationController : Controller`, `[Route("api/[controller]")]`. Has GET (all), POST (create), DELETE. Add `[Authorize]`.
  - `BillingNotificationService/Controllers/BillingNotificationController.cs` — class `BillingNotificationController : Controller`. Line 11 is `//[Authorize]` — uncomment it (and add the `using Microsoft.AspNetCore.Authorization;` if needed). Has GET (all/by-id), POST, PUT, DELETE.

The JWT is issued by AnonymousUserService; signing key/issuer/audience come from env vars / `appsettings.json` (see existing authenticated services for the exact `JwtSettings`/`Jwt` keys). Match that configuration so tokens minted by the system validate here.
- The producers (tasks 002–005) forward `Request.Headers["Authorization"]`, so once `[Authorize]` is on, authenticated producer calls keep working and anonymous calls are rejected.
- Test pattern: existing notification test projects use xUnit + Moq + `EF InMemory`; for the 401 assertion you may use `WebApplicationFactory` (integration) or a controller-level check, matching whatever scaffolding already exists in those test projects.

- Don't change the create-DTO shapes — producers depend on them being exactly as documented in task 001.
- The frontend currently calls these via the gateway with a bearer token from AuthContext for the org pages; confirm the org-page display path still sends a token (display is out of scope to change, but don't break it).

## Solution

Both notification controllers are now `[Authorize]`d and both services validate JWTs.

- `SystemNotificationController`: added `[Authorize]` + `using Microsoft.AspNetCore.Authorization`.
- `BillingNotificationController`: uncommented `[Authorize]` (+ using).
- Program.cs (both): added `AddAuthentication(JwtBearer).AddJwtBearer(...)` and inserted
  `app.UseAuthentication()` before `app.UseAuthorization()`. Validation is **multi-issuer /
  multi-key**: accepts tokens from BOTH system issuers (`AnonymousUserService` and
  `OrganizationService`) so producer-forwarded anon- or org-user bearers validate, and the
  frontend org page (org token) keeps reading notifications. Issuers/audiences/keys read from
  the `Jwt` section in appsettings.json; keys list includes both the local dev keys and the
  docker secret keys, so tokens validate in both environments without a docker-compose change.
- `SystemNotificationService.csproj`: added `Microsoft.AspNetCore.Authentication.JwtBearer`
  8.0.24 (Billing already had it).
- Tests (both services pass): existing WebApplicationFactory integration CRUD tests now attach
  a valid system-issued bearer (new `TestJwt` helper + `System.IdentityModel.Tokens.Jwt` 8.14.0)
  so they pass under `[Authorize]`; new `*AuthTests` assert no-token GET/POST -> 401. Also fixed
  two pre-existing notification test bugs that were failing on base independently of auth
  (a `List<>`-vs-array assertion in `SystemNotificationTests`, and an order-dependent empty-list
  integration test). Unit/controller tests are unaffected by `[Authorize]` (direct method calls).

Verified: `SystemNotificationServiceTests` 12/12 and `BillingNotificationServiceTests` 31/31 pass.

### Verdict

`accurate` — `[Authorize]` enforced, middleware order correct, JWT config verified against the
real issuers in both environments, tests pass.

Minor follow-up (non-blocking): the Docker secret keys are duplicated into the committed
`appsettings.json` `Jwt:Keys`. The real issuer services receive their docker key via the
`Jwt__Key` env var (uncommitted); the notification services have no equivalent `Jwt__Keys`
env override in docker-compose, so a future rotation of the issuer secrets would not propagate
here and would cause silent 401s (notifications are non-fatal -> dropped). Recommend sourcing the
keys from env/secret rather than committing them. Not required for current functionality.
